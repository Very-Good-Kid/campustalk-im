# 校园即时通讯系统 · 架构与数据设计

> 项目定位：面向高校班级与社团的 Web 即时通讯系统。熟人聊天（私聊 / 群聊）为主轴，兴趣频道为差异化切口。
> 技术栈：FastAPI + 原生 WebSocket + MySQL 26.7 + Vue3
> 周期：单人，约 3 周

---

## 一、产品定位（一句话）

面向高校班级与社团的即时通讯工具——熟人聊天照做，外加校园身份（学号 / 院系 / 班级）和话题频道内容沉淀。

**与任务的关系**：任务要求的 8 条功能（界面、注册、登录登出、好友管理、个人信息、单聊、群聊、文件图片表情）全部照做，一条不落；"社区论坛"那个参考产品通过"兴趣频道"收进来，但不做完整的办公协同（审批 / 打卡 / 日程）。

---

## 二、四层架构

每一层只跟紧邻的下一层说话。

| 层 | 技术 | 职责 |
|---|---|---|
| 表现层 | Vue3 + Pinia | 7 个页面共用一套布局骨架；WebSocket 客户端；状态管理 |
| 接口层 | FastAPI | REST 管"会失败的操作"，WebSocket 只管实时投递，**两者不混用** |
| 业务层 | Python | 六个域，全系统只有这一层判断权限 |
| 数据层 | SQLAlchemy 2.0 async + aiomysql + MySQL 26.7 | 表结构由 Model 定义；图片文件存 `uploads/` 目录 |

外部依赖（虚线）：大模型 API —— W3 可选，做不完可砍。

---

## 三、六个域与独占表

每个表只有一个域能写，这是防止后期代码互相打架的关键。

| 域 | 管什么 | 独占的表 | 对外只提供这一个能力 |
|---|---|---|---|
| 身份 Identity | 注册、登录登出、JWT、个人资料、校园属性、头像 | `user` | 告诉我"这个 token 是谁" |
| 关系 Relation | 好友申请 / 同意 / 拒绝 / 删除、备注、分组、特别关注 | `friendship` | 告诉我"A 和 B 是不是好友" |
| 会话 Conversation | 建会话、成员管理、加入策略、历史可见性、置顶话题帖 | `conversation` `conversation_member` | 告诉我"这个人能不能进这个会话说话" |
| 消息 Message | 落库、历史拉取、实时推送、撤回 | `message` | 把消息存下来并推给该收到的人 |
| 内容 Content | 图片 / 文件上传、类型大小校验、生成 URL | 无表，落 `uploads/` | 给我一个文件，还我一个 URL |
| 机器人 Bot | 规则回复、（可选）AI 总结 | 复用 `message` | 作为特殊发送者产生消息 |

### 五条内部边界铁律

1. 消息域**不得直接查** `friendship` 表——判断"能不能发"必须问会话域。
2. WebSocket 处理函数**只搬运**，不做业务判断、不直接写库，一律转交业务层。
3. 文件只存 URL，**绝不**把二进制塞进 `message` 表或 WebSocket 帧。
4. 前端**不持有任何业务规则**——它只负责把后端的拒绝理由显示出来。
5. 机器人域**不得自己插** `message` 表，必须走消息域的接口。

## 四、系统边界

**做**：注册、登录登出、个人资料修改、好友增删改与备注分组、单聊、群聊、频道、文本 / 表情 / 图片 / 文件、历史消息、消息撤回（3 分钟内）、未读红点、规则机器人、（可选）AI 总结。

**不做**：音视频通话、朋友圈动态、支付红包、端到端加密、原生移动端、扩列式陌生人匹配、按班级自动建群、审批 / 打卡 / 日程、已读回执、离线推送、多端同步。

**技术栈边界**：Redis 仅做 Pub/Sub 广播总线（瞬态通道，不存持久数据，连接表仍进程本地）；明确不引入消息队列（AI 总结用 `BackgroundTasks`）、Nginx、对象存储（本地 `uploads/`）、Docker Compose、微服务拆分。

**部署边界（必须遵守）**：仅在本机 `localhost` 运行，不购买域名、不做 ICP 备案、不做内网穿透、不对外提供服务。这是内容合规的前提——一旦对外提供服务，平台性质与法律责任都随之变化，详见《内容安全与合规设计》一节。

---

## 五、三种会话的权限边界

"统一会话抽象"的真正价值：权限差异全部集中在这张表里，代码其他部分完全一样。

| 能力 | 私聊 single | 群组 group | 频道 channel |
|---|---|---|---|
| 谁能加入 | 双向好友自动成立 | 邀请或申请后群主同意 | 任何人免审直接进 |
| 谁能发消息 | 双方 | 成员 | 成员 |
| 谁能拉人 | — | 群主 / 管理员 | 不用拉，自己进 |
| 谁能移除成员 | — | 群主 | 创建者 |
| 谁能改名称头像 | — | 群主 | 创建者 |
| 谁能置顶话题帖 | — | — | 创建者 |
| 历史消息对新成员 | 全部 | **由群主配置** | 全部公开 |
| 能不能退出 | 删好友即消失 | 可退群 | 可退出 |

## 六、接口边界

- **REST** 负责会失败的操作：注册登录、好友、资料、会话、历史消息、文件上传。
- **WebSocket** 只负责实时投递：`/ws?token=xxx`。帧类型只有 4 种：`send_message` / `receive_message` / `typing` / `system_notice`（撤回通知、AI 总结都走 `system_notice` 或 `receive_message`）。
- **认证**：REST 走 `Authorization: Bearer <jwt>`；WebSocket 连接时 query 带 token，校验失败直接关闭连接。

## 七、非功能需求

内容安全属于非功能需求，不占功能点，但体现设计完整性——多数学生项目的这一节是空的。

| 类别 | 要求 | 验收方式 |
|---|---|---|
| **安全性** | 密码哈希存储（绝不存明文）；JWT 鉴权；所有接口校验身份；越权访问返回 403 | 用 A 的 token 请求 B 的会话，应被拒绝 |
| **合规性** | 内容敏感词过滤（后端拦截）；注册勾选用户协议；操作日志可追溯；**仅本机运行、不上公网** | 发送含敏感词的消息被拒绝；`report` 表记录完整 |
| **性能** | 单群 5000 条消息内，历史拉取与翻页无明显卡顿（< 500ms） | `message(conversation_id, created_at)` 联合索引生效 |
| **实时性** | 消息从发送到对方可见 < 1s（同一局域网内） | 两个浏览器窗口实测 |
| **易用性** | 7 个页面布局统一（顶栏 + 左侧列表 + 右侧内容）；新用户无需文档即可走完"注册 → 加好友 → 发消息" | 现场找同学盲测 3 分钟 |
| **可靠性** | 消息先落库再推送；刷新后历史不丢；AI 功能失败不阻塞主流程 | 刷新页面、断网重连验证 |
| **可维护性** | 每个表只有一个域可写；业务规则集中在业务层，前端不持有规则 | 代码走查 |

## 八、核心表字段详解

> 本节列 5 张核心表。第 6 张 `report`（举报记录）为 W3 可选项，见《内容安全与合规设计》一节。

### 1. user（用户表）

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| id | Integer PK 自增 | 否 | 主键 |
| student_id | String(32) unique | 是 | 学号，校园身份核心。可空是因为机器人账号没学号 |
| username | String(50) unique | 否 | 登录名 |
| password_hash | String(255) | 否 | 存哈希，**绝不存明文** |
| nickname | String(50) | 否 | 昵称，聊天界面显示 |
| avatar_url | String(255) | 是 | 头像路径，用默认头像时为空 |
| bio | String(200) | 是 | 个性签名 |
| department | String(100) | 是 | 院系，用于"找同院系的频道" |
| class_name | String(100) | 是 | 班级，用于"找同班同学" |
| **is_bot** | Boolean 默认 False | 否 | 机器人 / AI 虚拟账号标记（预留） |
| created_at | DateTime | 否 | 注册时间 |
| last_seen_at | DateTime | 是 | 最后在线时间，用于显示在线状态 |

### 2. friendship（好友关系表）

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| id | Integer PK | 否 | 主键 |
| user_id | FK → user.id | 否 | 关系的持有者 |
| friend_id | FK → user.id | 否 | 对方 |
| status | String(20) | 否 | `pending` / `accepted` / `rejected` |
| remark | String(50) | 是 | 备注名（对应"修改好友信息"要求） |
| group_name | String(50) | 是 | 分组名，如"同班""社团"。**不独立建表** |
| is_starred | Boolean 默认 False | 否 | 特别关注 |
| request_message | String(200) | 是 | 好友申请附言 |
| created_at | DateTime | 否 | 申请发起时间 |
| updated_at | DateTime | 是 | 状态变更时间 |

- 唯一索引：`(user_id, friend_id)`
- **必须存两条**：A 加 B 同意后，要同时写 `(A,B,accepted)` 和 `(B,A,accepted)`。因为备注和分组是各人各自的——我给 B 起的备注不该出现在 B 的好友列表里。
- 申请流程：插入一条 `pending` → 对方同意改成 `accepted` 并反向补一条；拒绝改成 `rejected`（或直接删除）。

### 3. conversation（会话表）

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| id | Integer PK | 否 | 主键 |
| type | String(20) | 否 | `single` / `group` / `channel` |
| name | String(100) | 是 | 群 / 频道名；私聊为空，前端拼对方昵称 |
| avatar_url | String(255) | 是 | 群 / 频道头像 |
| owner_id | FK → user.id | 是 | 群主 / 频道创建者；私聊为空 |
| description | String(500) | 是 | 频道简介、群公告 |
| **history_visible_mode** | String(20) 默认 `all` | 否 | `all` / `since_join` / `recent_n`，新成员能看多少历史 |
| **history_limit** | Integer 默认 20 | 是 | 仅 `mode=recent_n` 时生效。**不在枚举里写死数字** |
| created_at | DateTime | 否 | 创建时间 |

- `history_visible_mode` 仅对 `group` 生效；`channel` 恒为 `all`，`single` 恒为 `all`。
- 三种模式的查询差异：
  - `all`：一条 SQL，游标分页
  - `since_join`：多一个条件 `created_at >= joined_at`
  - `recent_n`：先查第 N 条的 `created_at` 作为下界，再多一个条件（多一次查询）

### 4. conversation_member（会话成员表）

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| id | Integer PK | 否 | 主键 |
| conversation_id | FK → conversation.id | 否 | 所属会话 |
| user_id | FK → user.id | 否 | 成员 |
| role | String(20) 默认 `member` | 否 | `owner` / `admin` / `member` |
| **joined_at** | DateTime | 否 | 加入时间，**历史可见性判断用** |
| **last_read_message_id** | Integer | 是 | 已读到的最后一条消息 id，**未读红点用** |
| is_muted | Boolean 默认 False | 否 | 免打扰（可选） |

- 唯一索引：`(conversation_id, user_id)`
- **未读红点 ≠ 已读回执**：已读回执是"对方看没看我的消息"（不做），未读红点是"我有多少条没看"（做）。
- 未读数查询：
  ```sql
  SELECT COUNT(*) FROM message
  WHERE conversation_id = ?
    AND id > :last_read_message_id
    AND sender_id != :me
    AND recalled_at IS NULL
  ```

### 5. message（消息表）

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| id | Integer PK | 否 | 主键 |
| conversation_id | FK → conversation.id | 否 | 所属会话 |
| sender_id | FK → user.id | 否 | 发送者，可以是 bot 账号 |
| **msg_type** | String(20) | 否 | `text` / `image` / `file` / `emoji` / `system` / `ai_summary` |
| **sender_type** | String(20) 默认 `user` | 否 | `user` / `bot` / `system` —— AI 与机器人的入口 |
| content | Text | 否 | 文本存文本；图片 / 文件存 URL；撤回后原文保留 |
| file_name | String(255) | 是 | 文件原名 |
| file_size | Integer | 是 | 字节数 |
| reply_to_id | FK → message.id | 是 | 回复哪条消息（字段先留，UI 可选做） |
| **recalled_at** | DateTime | 是 | **撤回标记，不是删除** |
| **is_pinned** | Boolean 默认 False | 否 | 频道置顶话题帖 |
| created_at | DateTime | 否 | 发送时间 |

- **必须建索引**：`(conversation_id, created_at)` —— 拉历史和分页全靠它。
- 游标分页（往上翻加载更多）：
  ```sql
  SELECT * FROM message
  WHERE conversation_id = ? AND created_at < :cursor
  ORDER BY created_at DESC LIMIT 20
  ```
- 撤回逻辑：`now - created_at <= 180s` 且 `sender_id == me` → 置 `recalled_at = now()`，**并广播 WebSocket 通知**，否则对方界面不变。
- 四个加粗字段（`msg_type` / `sender_type` / `recalled_at` / `is_pinned`）是后面所有扩展的入口，W1 就要留好。

### 不入库的东西

`uploads/` 目录放图片和文件本体，数据库只存 URL + 文件名 + 大小。**绝不把二进制写进数据库。**

## 九、关键设计决策记录

| 决策 | 结论 | 理由 |
|---|---|---|
| 频道实现方式 | 复用群聊，只多"免审加入 + 置顶话题帖" | 成本约 +15%，报告里能独立成章 |
| 校园身份 | 学号 + 院系 + 班级，提供"找同班同学""按院系检索频道" | 不做"按班级自动建群"——没有教务数据只能造假 |
| 历史可见性 | `mode` 枚举 + `limit` 整数两个字段 | 不在枚举里写死 20/50，改数字只改配置 |
| 消息撤回 | 做，3 分钟限制，标记而非删除 | 老师爱看，半天工作量；不做已读回执 |
| 未读红点 | 做（不是已读回执） | 一个字段换界面质感 |
| AI 总结 | W3 末段，做不完可砍，必须优雅失败 | 老师四条评分标准一条都不占 |
| 数据库 | MySQL 26.7（本地 3306，库名 campustalk，utf8mb4）+ aiomysql 异步驱动 | 不写裸 SQL、只用通用类型、时间存 UTC；连接串集中配置，从环境变量读 |

## 十、内容安全与合规设计

### 责任归属（必须先搞清楚）

**法律责任主要由平台运营者承担，不是发帖用户。**

- 网络运营者对其用户发布的信息负有管理义务：发现违法信息应当立即停止传输、采取消除等处置措施、防止扩散、保存有关记录，并向主管部门报告。
- 网络日志留存不少于六个月。
- 即时通信工具遵循"**后台实名、前台自愿**"原则。
- 拒不履行上述义务且情节严重的，可能触及刑事责任。

> 上述为原则性表述，具体条款以现行有效法律文本为准。报告引用前请自行核对原文，不要照抄。

**关键分水岭是"是否对外提供服务"**：只在本机 `localhost` 演示、不买域名不备案不上公网，实际风险接近于零；一旦部署到公网，性质完全不同。因此**"不上公网"是正式的系统边界**，见第四节。

### 校园身份是天然合规优势

学号注册恰好实现了"后台实名"——用户知道自己实名，行为天然收敛。这一点应写进报告，它把"校园场景"从产品卖点升级为合规设计。

### 三道防线

| 阶段 | 目标 | 措施 |
|---|---|---|
| 事前 | 不敢发 | 学号注册（后台实名）、注册勾选用户协议与社区规范、频道创建者负责制 |
| 事中 | 发不出 | 敏感词过滤、图片先存后审。**免审进入 ≠ 免审发言**，这两件事必须在设计上分开表述 |
| 事后 | 追得到 | 一键举报、删帖 / 禁言 / 封号、操作日志留存 |

### 落地清单

| 优先级 | 事项 | 成本 |
|---|---|---|
| W1 必做 | 敏感词过滤（词库 txt + 发送时后端匹配，命中即拒绝） | 约 10 行代码 |
| W1 必做 | 注册页勾选用户协议 | 前端 5 分钟 |
| W1 必做 | 部署边界写死：只跑 localhost | 不写代码 |
| W3 建议 | 举报 + 管理员处置页 + `report` 表 | 约半天 |
| W3 建议 | 频道创建者可禁言 / 移除成员 | 顺手实现 |
| 只写不做 | 完整治理机制、日志留存 6 个月、分级处置、AI 生成内容合规 | 报告章节 |

### 可选的第 6 张表：report（举报记录）

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| id | Integer PK | 否 | 主键 |
| reporter_id | FK → user.id | 否 | 举报人 |
| message_id | FK → message.id | 否 | 被举报的消息 |
| reason | String(200) | 否 | 举报理由 |
| status | String(20) | 否 | `pending` / `resolved` / `rejected` |
| handled_by | FK → user.id | 是 | 处理人（管理员） |
| handled_at | DateTime | 是 | 处理时间 |
| created_at | DateTime | 否 | 举报时间 |

注：本表为 W3 可选项，W1/W2 不加。

### 归类与话术

内容安全属于**非功能需求**，应写入需求分析的"非功能需求"一节（安全性、合规性），不占功能点但体现设计完整性。

设计取舍问答（应对"单人项目搞这么复杂有必要吗"）：

> 虽然是单人项目，但只要涉及用户生成内容，平台的内容管理责任就是法定义务，不是可选功能。我在设计阶段就把它作为非功能需求纳入，实现成本只有几十行代码；但如果完全缺失，这个系统在合规上是不可上线的。

## 十一、排期与验收现象

| 周 | 主线 | 周末必须看到的现象 |
|---|---|---|
| W1 | 建表、注册登录、WebSocket 打通、页面骨架、**敏感词过滤 + 用户协议勾选** | 两个浏览器窗口互发一条纯文本，刷新后消息还在；发含敏感词的消息被后端拒绝 |
