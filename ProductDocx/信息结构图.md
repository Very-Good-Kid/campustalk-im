| # | 问题 | 严重性 | 修改方向 |

## 六、频道形态定稿与「群表复用」边界（2026-09-10 13:08 宝拍板）

### 6.1 形态定稿：论坛 / 朋友圈，不是公众号

| 维度 | 公众号 / 订阅号（❌ 不采用） | 论坛 / 朋友圈（✅ 采用） |
|------|--------------------------|----------------------|
| 关系 | 1 对多，单向推送 | 多对多，成员互相可见 |
| 谁能发 | 只有号主 / 管理员 | 所有成员都能发帖 |
| 互动 | 基本无，或仅精选留言 | 评论、回复、点赞 |
| 进入方式 | 关注 / 订阅 | **加入 / 退出频道** |
| 内容组织 | 按发布时间推送 | 帖子流（按时间 / 按热度）+ 话题标签 |
| 内容属性 | 即时消费，沉淀弱 | **内容沉淀**，可回溯 |

### 6.2 频道 vs 群聊：真正的差异点

| | 群聊 | 频道 |
|---|---|---|
| 载体 | 消息流（实时） | 帖子（异步、可沉淀） |
| 组织维度 | 围绕**人**（一群人聊天） | 围绕**话题**（一个话题下的内容） |
| 时效性 | 高，刷屏即过 | 低，可检索回溯 |
| 排序 | 严格时间序 | 时间 / 热度 / 置顶 |

> 一句话：**群聊是"一群人实时说话"，频道是"一个话题下的内容沉淀"。**

### 6.3 「复用群表」的边界（重要，影响第 2 章 E-R 图）

之前拍板的"复用群表 + `channel_flag`"（**勘误：实际代码用 `conversation.type` 枚举，无 `channel_flag` 字段**）是建立在"频道 = 群聊变体"的假设上。形态改为论坛 / 朋友圈后，复用范围需要收窄：

| 层 | 内容 | 能否复用群表 | 说明 |
|---|------|------------|------|
| **容器层** | 频道名、简介、头像、成员、管理员 | ✅ **可以** | 与群聊同构，用 `conversation.type='channel'` 区分（**容器层已实现**） |
| **内容层** | 帖子、评论、点赞、置顶、话题标签 | ❌ **不能** | 群聊的 `message` 表装不下：帖子需要 点赞数 / 评论数 / 置顶位 / 话题标签，且是非实时内容 |

**结论**：新增 3 张表 —— `post`（帖子）、`comment`（评论）、`like`（点赞），**均已实现**（见第 2 章 2.4）。

### 6.4 频道本期范围：方案 B（宝 2026-09-10 14:01 拍板）

**帖子 + 评论 + 点赞全量**，新增 3 张表 + 对应 API + 前端页面。

被否掉的方案：

| 方案 | 内容 | 未采用原因 |
|------|------|-----------|
| A | 仅帖子，评论点赞后期 | 功能不完整，"社区"感立不住 |
| C | 仅容器，内容全后期 | 频道会退化成"另一个群聊" |

### 6.5 频道独立为主分支（宝 2026-09-10 14:01 拍板）

频道从 ③ 群聊 下移出，独立为 **⑥ 内容社区（频道）**。

**理由**：频道形态已确定为论坛 / 朋友圈式内容社区，与"实时聊天"是两类产品形态。参照微信的做法——「聊天」和「朋友圈」是平级模块，不是包含关系。继续挂在群聊下会让人误以为它是群聊的子类型。

对应调整：
- ③ `群聊·频道` → ③ `群聊`
- 新增 ⑥ `内容社区（频道）`，配色 `c-blue`（与其余 5 域区分）

### 6.6 第 2 章《系统设计》三张表（已实现）
